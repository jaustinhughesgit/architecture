# Sentence, Essence, Path, Command, Menu, and Automation Runtime

**Status:** Implemented foundation; partial formal specification

These components form one interaction runtime. They let natural input become reusable local behavior instead of requiring a model call for every repeated request.

## Processing chain

```text
sentence or voice
  -> token and linguistic analysis
  -> exact or structural signature
  -> installed Path match, or required Path proposal/validation on a cold miss
  -> browser-local canonical Essence materialized from the installed Path
  -> ContextDB read/write, command, menu transition, automation, or entity call
  -> response and reusable learning evidence
```

## Terms

- **Sentence:** The user's original utterance. It remains evidence and repair context; it is not the durable executable representation by itself.
- **Essence:** A compact semantic operation over actors, relations, values, properties, modifiers, and questions. It is the bridge between language and ContextDB behavior.
- **Derived operation:** A read-only Essence row that combines values already bound by graph-query rows. Arithmetic uses `{op:add}`, `{op:subtract}`, `{op:multiply}`, or `{op:divide}` with a result variable and two operands. Identity aggregation uses `{op:count}` with one bound set operand. Neither form mutates ContextDB.
- **Signature:** The reusable match shape computed from an utterance, such as token lemmas/tags or a typed structural pattern with captures.
- **Path:** A tested mapping from a signature or semantic family to an executable transform. Its left side recognizes language; its right side performs a query, mutation, command, or capability invocation.
- **Command:** A named, declarative action and target published into the browser command registry. Commands provide safe entry points to entities, functions, routes, UI actions, or other registered behavior.
- **Menu:** A stateful set of available commands and calls. Menus expose contextual choices and transitions rather than requiring every action to be a globally active phrase.
- **Call:** A menu/state transition that can show, hide, run, go back, close, or expose options through the same command channel.
- **Automation:** A sequenced queue of delays, speech, commands, and related interaction events. It composes registered behavior; it does not replace Paths or the external task scheduler.
- **Sequence:** A composition of saved equations/operations into a reusable multi-step transform.
- **Function:** Executable implementation referenced by entity actions. Functions run within the entity/runtime trust boundary and require validation and policy controls.

## Why the whole chain matters

A correct Essence with a bad signature will not match later wording. A correct signature with a bad Path transform will retrieve or mutate the wrong data. A correct Path that invokes the wrong command or menu state still produces bad behavior. Editing therefore needs the sentence, Essence, ContextDB traverse, matching signatures, Path transforms, command/menu definitions, and relevant entity contract together.

## Builder behavior

- Canonical Essence is materialized in the browser from an installed, validated Path. A cold miss has no executable Essence: a model may propose a Path, but that proposal must be compiled, tested, installed, and replayed locally before ContextDB is touched. A server or model-generated Essence is never the semantic authority for the request.
- Missing required Path coverage and optional coverage expansion are separate lifecycles. The current wording's required Path is built, validated, saved, installed, and replayed even when **Auto-build Path signatures with OpenAI** is disabled.
- An installed Path that matches syntax but fails its local answer or transaction contract is defective coverage, not successful reuse. It enters required Path repair regardless of the optional Auto-build setting; the failed Path is retained only as repair evidence until a locally tested replacement or revision is installed.
- Reusable semantic operations such as event observation, signed quantity observation, distinct counting, and summation are declared as versioned data. Language such as “sold,” “restocked,” or “received” belongs to Path definitions that bind those operations; it is not procedural vocabulary in the browser runtime.
- Ordinary clauses that describe an occurrence may bind the vocabulary-neutral activity-observation entity. Its stable graph contract separates actor, normalized activity, optional object and kind, participants, object ownership and descriptors, directly entailed result relationships, modifiers, quantity/unit, and browser-local observation time. It provides projections for actor, object, descriptor, quantity, and an owner-qualified result subject. A model chooses predicates and typed bindings; runtime code does not branch on verbs or example domains. Safe token bindings become typed structural slots by binding type before installation.
- **Auto-build Path signatures with OpenAI** controls only additional ways the same canonical interaction could have been expressed. When enabled, OpenAI may propose extra paraphrase Paths with their own explicit source text, local Essence equivalence, signatures, and tests. When disabled, only the required current Path is requested.
- A model proposal may broaden cross-browser wording coverage, but it cannot replace or amend the canonical local Essence. This keeps identical installed Path versions semantically consistent across browsers and preserves the zero-trust execution boundary.
- When the browser promotes a learned exact-token proposal into a reusable structural Path, it owns an atomic schema-v3 compilation of both sides: typed structural recognition on the left and the versioned deterministic semantic transform on the right. Model output that uses an older or incomplete proposal shape is normalized and locally retested before persistence; it is never stored as the execution contract verbatim.
- If the proposal selects an installed semantic-entity operation, the model supplies only the operation reference and typed bindings. The browser discards model-authored executable rows, conditions, transactions, and answer templates and regenerates them from the installed entity version before the local tournament. The tested browser-compiled transform is the transform persisted with the Path.
- Proposal ingress applies the same authority boundary before server validation: a selected catalog operation replaces model-authored executable fields before binding-reference and row checks. This prevents invented low-level rows from causing repeated repair attempts while leaving the browser compiler as the final execution authority.
- Proposal ingress now treats the model's selected operation and typed bindings as Semantic Plan v1. A deterministic Path Synthesis Compiler constructs the exact left matcher and catalog-owned right transform, so matcher coverage and executable JSON are compiler outputs rather than fields the model must repair probabilistically.
- Semantic operations may declare `localSyntaxPlans` that map named structural triplet cells into typed operation roles. Compatible compiler-derived candidates are tested beside the model candidate against the model's adjudicated answer; they are required-current alternatives, not Auto-build paraphrases.
- Path-repair transport preserves `adjudication` through the final server response so the browser receives statement graph-row requirements, historical repair relationships, and question proof targets.
- For a catalog-backed statement, required graph rows are regenerated from the compiled semantic operation. Raw adjudicated rows are retained separately for diagnosis; the browser materializes canonical binding and instance references before comparing the candidate's graph effects.
- Supporting-source discovery can traverse bounded ContextDB adjacency from recent typed binding values, allowing specific entities and their stored broader classifications to participate in the same atomic repair without vocabulary rules. Catalog `repairWhen` plus `bindingDerivations` can refine an unresolved generic role from a current query binding while the adjudicated answer remains the required local proof.
- The worker hydrates the versioned semantic-entity catalog independently of Path installation. Existing cached Paths do not eliminate the definitions needed to compile a later cold-miss candidate.
- Candidate bindings outside the selected operation contract are removed before compilation. A source token promoted only for a removed binding is restored as fixed Path grammar and the structural signature is recomputed, preventing an unused model binding from becoming a wildcard.
- Structural family aliases execute with their own signature, pattern, and extraction bindings while reusing the canonical transform. The alias signature participates in the same v3 integrity check as a canonical Path.
- Identity-scoped server persistence must round-trip every browser-validated active alias before worker installation is acknowledged. The target identity owns the Path record; an optional creator-audit index is written only when a nonempty authenticated creator identity is available, never as an empty key or an inferred actor. Alias compatibility follows the semantic answer contract: deterministic numeric operators such as sum, subtraction, count, and division are quantity answers, not unrelated answer categories that may be removed during migration.
- Startup hydration is a versioned handoff: cached Paths may provide an immediate fallback, the authoritative identity-scoped result must supersede them, and stale responses for a prior identity must be ignored. Worker readiness requires the installed Path identities—not merely a nonzero count—to match the latest published set. New user input waits until both the local foundation and identity hydration are ready; an explicit hydration failure may release the identity-scoped local cache, but an in-flight server response cannot be interpreted as evidence that a saved Path is missing.
- Every browser-local semantic artifact is identity-scoped, including the learned Path library, graph snapshots, ContextDB state, word maps, transcription history, translations, and their local encryption keys. Navigating to another primary identity clears prior in-memory Paths and pending replication before hydrating the selected identity; an unowned legacy cache is not migrated. The selected account cannot inherit equations or graph identifiers from the previous account.
- A linguistic signature match is not sufficient for question success. The materialized Path must resolve a non-empty answer against the current identity's graph; an empty projection is rejected as a stale or incomplete Path and becomes repair evidence.
- Model output is candidate Path-learning evidence, never a successful Essence fallback for browser execution.
- Candidate Paths must be tested in the same local runtime that will execute them, against the worker-authoritative current ContextDB rather than a graph copy captured before a resumable model round trip.
- Candidate validation includes semantic coverage as well as token coverage. An explicit typed source value cannot be accepted merely because its token was frozen into the signature: a cardinal in a statement must survive local compilation as a numeric binding owned by the selected semantic operation. The same invariant is available to future typed-role contracts.
- Typed Path promotion resolves an unambiguous nested descriptor/noun-head overlap into separate linear slots before testing and persistence. If removing typed nested spans does not leave one contiguous noun-bearing head, promotion fails rather than guessing or dropping a binding. When one possessive-pronoun entity binding has exactly one earlier non-pronoun resolved-entity antecedent, the compiler records an explicit binding reference even if the local tokenizer did not classify that antecedent as a person or proper name.
- Candidate expected-answer evidence is presentation-normalized before comparison. Case and insignificant whitespace cannot reject a correct canonical ContextDB value, while distinct normalized values still fail validation. Type or result-shape descriptions are never treated as literal expected values; they fall back to nonempty-answer and semantic-contract validation.
- A question can expose a defect in the Path that stored its supporting fact. The repair planner ranks relevant history by typed linguistic anchors and graph provenance, names the historical source block and missing semantic requirement, and requires a paired historical-statement/current-query proposal instead of retrying the query alone.
- Query operations can declare a versioned `repairSupport` graph contract. Before the first model response, the planner reports any uniquely matched historical Path missing that contract's roles; selecting the query then requires the supporting repair in the same atomic proposal set. Predicate bindings remain runtime references and are excluded from literal-vocabulary comparisons.
- A repair-support contract may declare compatible source operations, ordered alternate source bindings, and one `answerSourceBinding`. This permits a typed historical observation to migrate into a richer query graph and supplies a missing adjudication answer only when support discovery found one unambiguous, property-compatible value. The browser must still replay the supporting Path and reproduce that value locally before installation.
- A support graph contract may declare `bindingDerivations` from historical source bindings, current query bindings, or contract literals. The synthesis compiler uses those mappings to construct the supporting statement Path deterministically and replaces any model-authored version. This is dependency expansion over typed roles, not a word-specific workflow.
- Binding presence is not semantic proof. When a same-contract historical Path populated every required role but a query's declared predicate-bound role conflicts with the current predicate, support discovery requires model re-adjudication from the immutable historical sentence and local tokens. In that case deterministic derivation must not copy the defective executed bindings; the model-proposed historical repair and current query are accepted only through the ordinary atomic browser proof.
- Bounded repair transport must preserve the binding graph needed by those derivations: binding-to-binding references, token spans, value modes, scales, literals, and bounded executed scalar evidence. A compact history entry that says only `source: binding` without naming its source is malformed deterministic evidence; model retries cannot compensate for it.
- A semantic operation may declare `bindingDependencies` for roles that must co-vary. The compiler and normal materializer reapply the dependency whenever the Path executes; promoting an object token to a structural slot therefore cannot leave its kind or another declared dependent role frozen to the sentence that first created the Path.
- A catalog operation may declare `routingAliases` for an unavailable semantic-operation reference whose records are deliberately exposed through another installed capability. A route is eligible only when entity version, mode, operation identifier, and one declared source or target family prefix select a single installed operation. Declarative binding dependencies translate the source capability's typed roles—including time-window roles—into the target operation; runtime code does not branch on scenario vocabulary.
- Repeated semantic roles use typed local list bindings rather than retaining only the first token. For a coordinated object list, the Path owns the exact syntax and complete `nounList` span, while a catalog-owned `forEach` expands the locally extracted members into ordinary ContextDB rows. Semantic completeness rejects a statement candidate that binds only one member of an explicitly supplied list. Query Paths reuse the same activity/object relations and remain independent of the words or domain in the example.
- A transient provider rejection while creating a background Path-learning job may be retried once inside the same learning request. This bounded transport retry does not relax local candidate validation, add a semantic attempt, or execute/store the user input before a Path succeeds.
- A semantic operation may declare a `bindingPolicies` acquisition rule for roles that must generalize from the current utterance. `unique_matching_token` converts a model-supplied literal to the one source span that produces the same typed value and fails on zero or ambiguous matches. Only the catalog can authorize this conversion; equality with an input word alone never grants the core compiler permission to broaden a Path.
- Resulting relationship state uses the generic `contextdb.relationship-transition` capability. It stores the observed transition, affected object and kind, resulting subject/predicate, and a separate reference subject/predicate. A query can resolve an object through the reference relationship and project the subject of the resulting state. The LLM declares the semantic mapping in Path bindings once; subsequent matches execute it locally.
- A support contract can explicitly permit migration from an older observation operation. This repairs a historical Path that covered an object syntactically but stored it with a semantic entity unable to represent that object or resulting relationship.
- If both the older operation's repair and a migration contract match, `repairPriority` in semantic data chooses the preferred graph shape. The model receives that choice before generation, and server validation rejects a lower-priority selection with the exact replacement operation.
- Repair priority is grouped by answer contract. Subject, property, participant, count, and quantity projections do not compete across groups.
- `query_object_property_via_subject_relation` resolves a constrained object through any direct stored relationship from a known subject and projects a requested property. Predicate-variable joins make the same Path shape work through ownership, custody, responsibility, or another recorded association without deciding which relation a possessive must mean.
- Historical replay replaces its stored Path provenance as well as its graph delta. Review bundles therefore expose the semantic entity and bindings that produced the repaired Essence.
- Semantic-operation validation checks required roles twice: their binding definitions must have usable sources, and isolated execution must materialize nonempty values. A graph mutation containing a null required role cannot be promoted merely because it added relations.
- A binding may explicitly reuse the value of an earlier binding. This data-defined composition represents unambiguous coreference while keeping pronoun surfaces out of ContextDB identity. The browser may normalize a learned pronoun binding to the single compatible earlier entity binding; it must not guess when multiple antecedents remain possible.
- Once a correction round diagnoses a required query graph contract, subsequent rounds must retain that semantic operation and repair its supporting transaction. Switching to an unrelated operation is not a valid way to clear the failure, even if that operation happens to return a nonempty answer.
- A semantic query operation may declare which bindings must be grounded in the current utterance's predicate. Candidate validation checks those bindings against the typed predicate tokens before accepting an answer. This prevents a locally valid traversal from answering a state question with an unrelated event participant merely because that traversal returned data; the grounding requirement is operation metadata, not application vocabulary.
- Query operations may also declare compatible interrogative words as answer-role metadata. Validation therefore separates subject, property, quantity, and other projections before graph-support selection; an incompatible operation cannot lock correction into the wrong graph contract merely because it returned a value.
- Catalog compilation treats missing required bindings as fatal, while unusable optional bindings do not invalidate an otherwise complete operation. During a coordinated repair, an empty literal may be restored only from the prior Path's executed binding evidence for the same role; without such evidence, the optional binding and its conditional rows are omitted. This keeps cold-start correction strict without requiring the model to repeat already-proven optional metadata perfectly.
- Catalog operations may reject undeclared bindings rather than silently freezing them into grammar. This is used when losing a proposed role would make the stored graph semantically incomplete.
- Coordinated repair is one local proof transaction. The worker removes the selected block's prior graph effects in an isolated snapshot, materializes and replays the repaired statement, executes the current query against the resulting graph, and permits persistence only when every required Path passes. Persistence and live replay are rolled back as a unit on failure.
- Coordinated replay preserves an executed ContextDB node in both isolated proof and live commit only for a historical role whose repaired binding is token-sourced `resolvedEntity` and whose recorded value is a valid local entity identifier. Live orphan cleanup must not delete a node retained through such a binding. Deterministic discourse resolution runs before graph lookup or override: first-person, inclusive-plural, and second-person token mentions resolve to `speaker`, `listener_speaker`, and `listener`. `currentSpeaker` and binding-derived roles resolve from their declared current sources. Surface nouns, descriptors, scalars, and literals are still regenerated from the immutable local tokens and candidate Path; replay does not treat arbitrary historical values as authoritative overrides.
- Auto-build controls extra paraphrases only. Disabling it must not discard a replayable historical proposal required by a current repair transaction.
- Repeating the same typed semantic failure does not authorize blind model retries. After one corrected proposal repeats the same failed invariant, the runtime stops with a missing/insufficient semantic-capability diagnosis.
- Required Path generation and every correction round use resumable background model jobs. The browser polls with the complete opaque job descriptor and carries locally observed candidate failures into the next proposal; an API timeout must not decide whether an input can be learned.
- A locally validated learned Path may activate while retryable server replication is unavailable or the URL-selected primary identity has not completed its browser readiness handoff. It remains marked pending and is retried separately after identity becomes available. The Path runtime derives the same single-segment URL identity as the Primary module so module construction order cannot send an ownerless save. Durable Path persistence stores bounded validation summaries; full graph and candidate diagnostics remain in the browser review bundle rather than being duplicated into every Path record.
- A successful replication response is reconciled with the browser-proven family rather than replacing it. Server metadata and additional aliases may be accepted, but the round trip cannot discard an active alias validated by the current atomic transaction. Semantic-family identity mismatches and missing expected aliases fail before worker installation acknowledgement.
- Path Builder renders each canonical signature and active exact alias with the concrete sentence that created or tested it. Explicit confirmation promotes only that proven exact artifact into a retained shared foundation store. Confirmed Paths are merged into every identity’s initial hydration and are not deleted by the hard test reset; identity-scoped observations and unconfirmed Paths remain resettable.
- The post-reset `/newuser?reset=1` response expires the domain-scoped HttpOnly account token whose server record was deleted, allowing the next cold account bootstrap to establish a new identity instead of reusing a dead session.
- Typed captures must preserve distinct inputs such as actor, location, time reference, quantity, and projection.
- Statement Paths and question Paths have different safety rules: mutations require replay/idempotency controls; read-only queries can be tested without changing ContextDB.
- A Path signature recognizes and binds an intent; it does not justify creating executable behavior. If a typed Essence transaction fully represents a statement such as a fact, correction, or quantity delta, the Path must keep it on the local graph-mutation path.
- A rate, ratio, or “per” question must preserve both operands and its arithmetic operation. A candidate that merely projects one stored operand is semantically incomplete and must not be promoted.
- Wording aliases should share a canonical semantic transform when they truly mean the same thing.
- Conflicting canonical transforms must enter explicit repair/versioning rather than silently blocking the user's input or overwriting unrelated behavior.
- Corrections that refer to a recent role, event, or value are evaluated against the complete authorized browser-local graph. A bounded language-model context is not sufficient evidence for repair when it omits the relation being replaced.

The implemented semantic-coverage proof detects explicit numeric/cardinal loss plus omitted supplied people/proper nouns and descriptors, then executes paired historical/current repair transactions. The activity contract can materialize a directly entailed result relationship in the same provenance-bearing input block and query it through a declared traversal. General ontology inference and complete typed-role coverage remain partial; inferred support beyond a directly entailed relationship must carry machine-inference provenance and must not be presented as a user assertion.

## Commands, menus, and automations

Entities publish commands into a registry. Menus determine which commands are meaningful in the current state; calls move between states or execute registered behavior. Automations emit into that same interaction channel, allowing a voice/menu experience to compose ordinary entity behavior instead of maintaining a second command system.

## Derived arithmetic query rows

The browser-local query runtime supports deterministic binary arithmetic after ordinary ContextDB rows bind numeric variables. The row shape is:

```json
["*", "{result}", "{op:divide}", ["{numerator}", "{denominator}"]]
```

The operation is read-only, rejects unresolved or non-finite operands, and produces no result for division by zero. `{ask}` is used as the result variable when the derived value is the requested answer. Correlation remains an identity concern: operands should come from one record when possible, or from separately bound records constrained by the same owner and explicit modifiers when the stored facts are split. The runtime must not merge entities merely because their labels match.

## Required formalization

Versioned schemas are still needed for Essence operations, signature types, Path transforms, command targets, menu transitions, automation events, and sequences. The schemas must include permissions, side-effect classification, test fixtures, migration rules, and observable failure stages.
